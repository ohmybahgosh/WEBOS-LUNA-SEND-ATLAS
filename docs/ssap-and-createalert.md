# SSAP, the createAlert trick, and SSAP to luna mapping

SSAP is the websocket API (port 3000 / 3001) that phone apps and Home Assistant use to talk to the TV.  Under the hood it is a thin gateway over the Luna bus, so most SSAP URIs map directly onto luna URIs.  This page also documents the well known trick for reaching *private* luna methods without root.

> **Authoritative mapping:** a full SSAP->luna routing table with real required permissions, pulled from a retail webOS 7.0 TV, is in [ssap-routing-W22O.md](ssap-routing-W22O.md).  The table below explains the mechanism; that file has every concrete route.


## SSAP protocol essentials (from sources)

* Transport: websocket `ws://<tv>:3000` or `wss://<tv>:3001` (LG_Buddy, bscpylgtv `proto`/`port`).
* Messages: `{"type":"request|subscribe|register|hello", "id":"<any>", "uri":"ssap://<ns>/<method>", "payload":{...}}`. Responses: `{"type":"response|error|registered", "id", "payload"}`; payload has `returnValue`; subscriptions return `subscribed:true`. Error strings seen: `404 no such service or method`, `401 insufficient permissions`, `403 access denied`, `500 Application error`.
* `hello` message (bscpylgtv `getHelloInfo`) -> hello payload with device info. `register` message carries `manifest` (permissions list), `pairingType` (`PROMPT`, `PIN`, `COMBINED`, `LGSWITCH-PIN`), `forcePairing`, and `client-key` after pairing. PIN pairing finishes with `ssap://pairing/setPin {pin}`.
* Permission names (bscpylgtv manifest + LGTV Companion + homebridge-lgwebos-tv): LAUNCH, LAUNCH_WEBAPP, APP_TO_APP, CLOSE, TEST_OPEN, TEST_PROTECTED, TEST_SECURE, CONTROL_AUDIO, CONTROL_DISPLAY, CONTROL_INPUT_JOYSTICK, CONTROL_INPUT_MEDIA_RECORDING, CONTROL_INPUT_MEDIA_PLAYBACK, CONTROL_INPUT_TV, CONTROL_INPUT_TEXT, CONTROL_MOUSE_AND_KEYBOARD, CONTROL_POWER, CONTROL_TV_SCREEN, CONTROL_TV_STANBY (sic), CONTROL_FAVORITE_GROUP, CONTROL_USER_INFO, CONTROL_BLUETOOTH, CONTROL_TIMER_INFO, CONTROL_RECORDING, CONTROL_BOX_CHANNEL, CONTROL_CHANNEL_BLOCK, CONTROL_CHANNEL_GROUP, CONTROL_TV_POWER, CONTROL_WOL, READ_APP_STATUS, READ_CURRENT_CHANNEL, READ_INPUT_DEVICE_LIST, READ_NETWORK_STATE, READ_RUNNING_APPS, READ_INSTALLED_APPS, READ_TV_CHANNEL_LIST, READ_POWER_STATE, READ_COUNTRY_INFO, READ_SETTINGS, READ_STORAGE_DEVICE_LIST, READ_RECORDING_STATE/LIST/SCHEDULE, READ_TV_PROGRAM_INFO, READ_TV_ACR_AUTH_TOKEN, READ_TV_CONTENT_STATE, READ_TV_CURRENT_TIME, READ_UPDATE_INFO, READ_LGE_SDX, READ_LGE_TV_INPUT_EVENTS, READ_NOTIFICATIONS, WRITE_NOTIFICATION_TOAST, WRITE_NOTIFICATION_ALERT, WRITE_SETTINGS, WRITE_RECORDING_LIST, WRITE_RECORDING_SCHEDULE, CHECK_BLUETOOTH_DEVICE, STB_INTERNAL_CONNECTION, ADD_LAUNCHER_CHANNEL, SCAN_TV_CHANNELS, SET_CHANNEL_SKIP, RELEASE_CHANNEL_SKIP, DELETE_SELECT_CHANNEL, SEARCH, UPDATE_FROM_REMOTE_APP. Which permission gates which URI is only partly known: createAlert needs WRITE_NOTIFICATION_ALERT and (per LG_Buddy) also WRITE_NOTIFICATION_TOAST with an unsigned manifest, otherwise 401.
* Firmware differences (LG_Buddy docs/webos-testing.md): webOS 24 (9.2.2-61) accepts the legacy *signed* registration manifest (appId `com.lge.test`) and direct `ssap://settings/setSystemSettings`; webOS 26 (43.21.60, from LGTVCompanion issue #351) rejects the legacy signed certificate and direct SSAP settings writes, but accepts unsigned registration and the alert-backed luna route. LGTV Companion therefore ships manifest V1 (signed), V2 (signed section modified) and V3 (unsigned).
* Remote button socket: `ssap://com.webos.service.networkinput/getPointerInputSocket` -> `socketPath`; text protocol: `type:button\nname:<KEY>\n\n`, `type:move\ndx:..\ndy:..\ndown:0\n\n`, `type:click\n\n`, `type:scroll\ndx:..\ndy:..\n\n`. Button names in bscpylgtv `buttons.py`: LEFT RIGHT UP DOWN RED GREEN YELLOW BLUE CHANNELUP CHANNELDOWN VOLUMEUP VOLUMEDOWN PLAY PAUSE STOP REWIND FASTFORWARD ASTERISK BACK EXIT ENTER AMAZON NETFLIX 3D_MODE AD ADVANCE_SETTING ALEXA ASPECT_RATIO CC DASH EMANUAL EZPIC EZ_ADJUST EYE_Q GUIDE HCEC HOME INFO IN_START INPUT_HUB IVI LIST LIVE_ZOOM MAGNIFIER_ZOOM MENU MUTE MYAPPS POWER PROGRAM QMENU RECENT RECLIST RECORD SAP SCREEN_REMOTE SEARCH SOCCER TELETEXT TEXTOPTION TIMER TV TWIN UPDOWN USP YANDEX 0-9. (Also `tv:`-less keys like `type:button name:HOME`.) `lgtv2`'s README/`LGWebOSRemote` `instart.py` use the same socket to type the factory-menu PIN 0413.
* Service listing: `ssap://api/getServiceList` -> `{services:[{name,version}]}`. Old TV (snabb/webostv sample): api v1, audio v1, media.controls v1, media.viewer v1, pairing v1, system v1, system.launcher v1, system.notifications v1, tv v1, webapp v2. Newer TVs additionally accept the long-form `com.webos.*` URIs and `settings`, `config`, `externalpq`, `timer`, `user` etc. (all seen in code).
* The SSAP server side is `com.webos.service.secondscreen.gateway` + `com.webos.service.apiadapter` (webosbrew doc: `pkill -f ss.apiadapter; pkill -f ss.gateway`); URI -> luna routing is defined by `/usr/palm/services/com.webos.service.secondscreen.gateway/interfaces/<service>.interface` JSON files of the form `{"service":"<luna service>","methods":[{"path":"/<method>","description":"...","requiredPermissions":["LAUNCH"]}]}` (webosbrew system-mods guide). Apiadapter adapters include `adapters/settings/valid-settings.js` (the source of the whitelisted settings keys that bscpylgtv extracts into available_settings_*.md).

## The `createAlert` / `closeAlert` trick (invoke arbitrary luna URIs over SSAP without root)

Used by aiopylgtv/bscpylgtv (`luna_request`), LGTV Companion (`Event::createLunaPayload`), homebridge-webos-tv (`lunaSend`), homebridge-lgwebos-tv (`send('alert', ...)`), LG_Buddy, klattimer/LGWebOSRemote (README mentions), Hubitat driver. `ssap://system.notifications/createAlert` accepts alert *buttons* and `onclose`/`onfail` handlers whose `onClick`/`uri` is a luna URI that the TV itself invokes with the given `params`, with the privileges of the notification service. SSAP clients only get the alert's result back, **not** the luna call's return data. Pattern (bscpylgtv `luna_request`):

```json
{"type":"request","id":"1","uri":"ssap://system.notifications/createAlert",
 "payload":{"message":" ",
   "buttons":[{"label":"","onClick":"luna://com.webos.settingsservice/setSystemSettings","params":{"category":"picture","settings":{"backlight":"40"}}}],
   "onclose":{"uri":"luna://com.webos.settingsservice/setSystemSettings","params":{...same...}},
   "onfail": {"uri":"luna://com.webos.settingsservice/setSystemSettings","params":{...same...}}}}
```
then read `alertId` from the response and immediately send `ssap://system.notifications/closeAlert {"alertId": "<id>"}` - closing the alert fires `onclose`, which executes the luna call (the three redundant handlers are for robustness). Details by library:
* bscpylgtv/aiopylgtv: message `" "`, one empty-label button + onclose + onfail, then `closeAlert`.
* LGTV Companion: same payload; `alertId` closed as `com.webos.service.apiadapter-<N>` (it constructs the id itself, `JSON_LUNA_CLOSE_ALERT`).
* LG_Buddy: sees alert id prefixes `com.webos.service.apiadapter.pub-` (response) and `com.webos.service.apiadapter-` (close); needs `WRITE_NOTIFICATION_TOAST` in an unsigned manifest else createAlert returns 401.
* homebridge-webos-tv: payload `{title,message,modal:true,buttons:[{label:'Ok',focus:true,buttonType:'ok',onClick:<luna uri>,params}],onclose:{uri,params},onfail:{uri,params},type:'confirm',isSysReq:true}`; on webOS < 4 the alert must be opened twice and ENTER pressed on the remote socket because `closeAlert` is unavailable.
* homebridge-lgwebos-tv: same with `timeout:0`, `modal:true`, `type:'confirm'`.
* Confirmed working luna targets via the trick (code): com.webos.settingsservice/setSystemSettings, com.webos.service.eim/setDeviceInfo, com.webos.service.oledepl/setTemporalPeakControl + setGlobalStressReduction, com.webos.service.pqcontroller/setWhiteBalance + setProperties, com.webos.service.rollingscreen/changeCurve + updateCurvature, com.webos.surfacemanager/showInputPicker, com.webos.service.attachedstoragemanager/ejectDevice, com.webos.service.tvpower/power/turnOnScreenSaver, .../reboot, com.webos.service.tv.power/reboot, com.webos.service.config/setConfigs (the last five 'disabled at some point' / not working on newer webOS per bscpylgtv comments), com.webos.applicationManager/launch, luna targets are arbitrary - any service whose method is callable by the notification service's bus permissions. A luna URI is written without the `ssap://` prefix; in `luna_request()` the string is `luna://<service>/<method>`.
* Also seen: alert `onclick` buttons in root contexts (`webos-homebrew-channel startup.sh`) use key `onclick` (lower case) in `luna://com.webos.notification/createAlert`; SSAP-side clients use `onClick`.

## SSAP URI -> luna URI mapping

Basis legend: **NAME** = SSAP path starts with a full luna service name; per the gateway interface-file format (service + method path) the luna URI is `luna://<service>/<rest of path>` (this is how `com.webos.*` URIs behave; LGTV Companion's PowerShell examples even call `ssap://com.webos.service.audio/master/volumeUp`, a luna-style path, successfully); **STATED** = a source explicitly says so; **OBSERVED** = same call with same payload seen against luna directly; **UNKNOWN** = alias namespace; underlying luna service/method not shown in any source read (I did not guess).

| SSAP URI | luna URI | Basis |
|---|---|---|
| ssap://system.notifications/createToast | luna://com.webos.notification/createToast | OBSERVED (webos-homebrew-channel `createToast {message}`) |
| ssap://system.notifications/createAlert | luna://com.webos.notification/createAlert | OBSERVED (homebrew startup.sh uses buttons[{label,onclick,params}]) |
| ssap://system.notifications/closeToast, closeAlert | probably com.webos.notification/closeToast, closeAlert | UNKNOWN (not seen on luna side) |
| ssap://com.webos.applicationManager/launch | luna://com.webos.applicationManager/launch | NAME; luna form used by root tools and MagicRemoteService/webOSTV.js `launch` |
| ssap://com.webos.applicationManager/{open,close,getAppInfo,getForegroundAppInfo,listApps,listLaunchPoints} | luna://com.webos.applicationManager/<same> | NAME (getForegroundAppInfo, listApps, getAppInfo, launch also used on luna by glasshouse) |
| ssap://system.launcher/{launch,open,close,getAppState} | UNKNOWN (returns `sessionId`, whereas applicationManager/launch returns `processId`, so a different handler) | UNKNOWN |
| ssap://com.webos.service.tvpower/power/{getPowerState,turnOnScreen,turnOffScreen} | luna://com.webos.service.tvpower/power/<same> | NAME (getPowerState also on luna in glasshouse) |
| ssap://com.webos.service.tv.power/{turnOnScreen,turnOffScreen} | luna://com.webos.service.tv.power/<same> | NAME (webOS 4.0) |
| ssap://com.webos.service.update/getCurrentSWInformation | luna://com.webos.service.update/getCurrentSWInformation | NAME |
| ssap://com.webos.service.ime/*, networkinput/getPointerInputSocket, tv.display/*, appstatus/getAppStatus, connectionmanager/getinfo, attachedstoragemanager/listDevices, devicereset/requestReboot, panelcontroller/setScreenOnOff, eim/setDeviceInfo, surfacemanager/showInputPicker, media/getForegroundAppInfo, sdx/*, tv.keymanager/*, tv.time/*, miracast/*, bluetooth/*, appcasting/*, secondscreen.gateway/test/secure | luna://<same service>/<same path> | NAME |
| ssap://com.webos.service.apiadapter/audio/{getSoundOutput,changeSoundOutput} | apiadapter is the SSAP-side adapter service itself; no separate luna target found | UNKNOWN |
| ssap://com.webos.service.audio/master/{getVolume,setVolume,volumeUp,volumeDown} | luna://com.webos.service.audio/master/<same> | NAME |
| ssap://audio/{getVolume,setVolume,volumeUp,volumeDown} | probably luna://com.webos.service.audio/master/<same> (same payload `{volume}`, same `volumeStatus` response) | UNKNOWN/probable (not stated) |
| ssap://audio/{setMute,getStatus,getMute,changeSoundOutput,getSoundOutput} | UNKNOWN | UNKNOWN |
| ssap://tv/executeOneShot | luna://com.webos.service.capture/executeOneShot (webOS 9; `com.webos.service.tv.capture` on webOS 4 per glasshouse) | STATED (bscpylgtv docstring + LGTVCompanion docs) |
| ssap://settings/getSystemSettings | luna://com.webos.settingsservice/getSystemSettings (also `com.webos.service.settings/getSystemSettings` on newer builds) | OBSERVED (same {category,keys}; webOSTV.js, glasshouse) |
| ssap://settings/setSystemSettings | luna://com.webos.settingsservice/setSystemSettings | OBSERVED (same {category,settings}; public only on webOS 9+ and not on 26) |
| ssap://config/getConfigs | luna://com.webos.service.config/getConfigs | OBSERVED (same {configNames}) |
| ssap://externalpq/{setExternalPqData,getExternalPqData} | UNKNOWN (calibration API; luna service name not shown) | UNKNOWN |
| ssap://tv/* (channelUp/Down, getChannelList, getCurrentChannel, getChannelProgramInfo, getChannelCurrentProgramInfo, openChannel, getExternalInputList, switchInput, getACRAuthToken) | UNKNOWN | UNKNOWN |
| ssap://system/{turnOff,turnOn,getSystemInfo,getHostMessage}, ssap://media.controls/*, media.viewer/*, webapp/*, timer/*, user/*, pairing/setPin, api/getServiceList | UNKNOWN (gateway-internal) | UNKNOWN |

Luna-only methods (not offered over SSAP, only through the alert trick): see section 3 and records with `access: private`.
